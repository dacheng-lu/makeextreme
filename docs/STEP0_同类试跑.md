### 值得单独记下的一个缺陷（toolkit-v2）
审批门的判定是 `ck["awaiting_gate"] == sid` → 清除。第一次运行把 `awaiting_gate` 写成该阶段 id 并返回；**第二次运行不需要任何人操作，就会满足同一个条件而放行**。
即：暂停后只要再跑一次，门就开了。它自己的 7 项 selftest 全过（`ALL PASS`），因为 selftest 里"批准"是用 `gate_cleared` 手动设的，从没测过"没人批准时再跑"。这和我们的审批规则（F9）正好相反。
**教训**：审批必须是单独记录的事实，不能从"当前状态等于门的 id"推出。

## 探针自身的三次错误（已修，留档）
1. AC1 最初用 `sleep(8)` 的孤儿：续跑本身要跑 8 秒，孤儿自然退出，会把"没清掉"误判成"清掉了"。改为"首次执行睡 60 秒、重跑立即返回"。
2. 最初把"杀掉后立刻检查孤儿"当作 AC1a。这不是 ARCHITECTURE 里 AC1 的定义（"续跑后孤儿被清掉"），`kill -9` 的瞬间没人能清。已删。
3. DVC 的 AC5 先后错了两次：脚本没声明为依赖；随后 `open(f,"w").write(open(f).read())` 先清空再读。修正后 DVC 通过。第一次的"DVC 失败"是我的探针错，不是 DVC 错。

## kiso：为什么没运行
读了 `README.md` 和 `docs/durability.md`：它是"一个持久的 **agent 运行时** + 终端里的编码 agent"，Node ≥ 22，持久化对象是**模型轨迹 + 工具调用**（只追加的 JSONL 事件流，工具调用带按 `executionId` 的回执）。要驱动它必须接一个模型（登录 DeepSeek/Anthropic/OpenAI 或订阅），让 LLM 来调度各阶段。
我们的阶段是**事先已知、确定性的**流水线，把 LLM 放进调度环既不必要也不可复现。所以"能不能被 shell host 直接驱动、满足 AC1–AC4"这个准则在 kiso 上**不适用**，不是"没通过"。**这是依据 README 的推断，没有运行它的 `kill -9` 脚本证明**，我不据此断言它做不到它自己声称的事。

## 结论（对停止准则）
- **没有任何一个满足 AC1–AC4、AC7。** 按准则：**不采用，继续自己写。**
- 范围同时被缩小了——这是试跑的真正收获：
  - **AC5 不自己发明**：照 DVC 的做法（阶段指纹 = 命令 + 依赖内容哈希，记在锁文件里，不一致则失效）实现，约几十行，**不引入 DVC 依赖**（110 MB、需 Python 3.11、对我们只用到其中一个功能）。
  - **已知孤儿缺口用 kiso 的"未确定（uncertain）"思路闭合**：在 `Popen` **之前**先把"即将启动"fsync 进状态；续跑时发现"即将启动/运行中"但没有 pgid → 无法知道子进程是否存在 → 幂等阶段重跑，非幂等阶段停下等人决定。这是借想法，没借代码。
  - **审批（AC6）必须是独立记录**，并绑定被批准产物的哈希：产物变了，旧批准失效（借 ECC `operator-approval-loop` 的"哈希 + 纪元"想法，并避开 toolkit-v2 的上述缺陷）。
